## What lookup meant in 0.6.1

The preserved [adapter:217](../../build/v61_source/cellusbd_adapter.c:217) calls `c->real.location(0x425a0000+d, location)` directly in `buzz_cell_poll()`. It bypasses the wrapper. [native.c:278](native.c:278) assigns that pointer from `imports.patch[12].original`; the plan associates patch 12 with FNID `db819e03`, original game import slot **0x6fa424**, trampoline **0x5c97ec**. That export is **cellUsbdGetDeviceLocation**, independently identified in [PSDevWiki's FNID list](https://www.psdevwiki.com/ps3/Fnids.idh). It is not a device-enumeration API or a required LDD registration step.

The next gate, [preserved adapter:223](../../build/v61_source/cellusbd_adapter.c:223), requires DEVICE_NOT_FOUND (`8011000a`). Both calls instead returned `801100ff` in the supplied console log. The attempted bit is already set, so neither dongle is probed and neither is retried. No IN reports can reach the game, and configured/readiness stays false. Working pad tee and HTTP do not repair this gate.

**`0x801100ff` is CELL_USBD_ERROR_FATAL**, defined in [RPCS3 cellUsbd.h:26](https://github.com/RPCS3/rpcs3/blob/39fe6c2599f3f03b68940df1cad22305e78106b9/rpcs3/Emu/Cell/Modules/cellUsbd.h#L26) and [PSDevWiki's USB error table](https://www.psdevwiki.com/ps3/Template%3ACELL_ERROR_FACILITY_USB_-_0x011). It is a public library error, not a transfer completion code. [RPCS3 sys_usbd.cpp:1679-1694](https://github.com/RPCS3/rpcs3/blob/39fe6c2599f3f03b68940df1cad22305e78106b9/rpcs3/Emu/Cell/lv2/sys_usbd.cpp#L1679) takes `(handle, device_handle, location*)`, rejects uninitialized/unknown devices with **CELL_EINVAL**, otherwise copies the location and returns CELL_OK. **Inference:** passing an adapter-only device ID into the native library triggers its invalid-device/error path. The sources do not establish Sony's precise internal translation from LV2 error to FATAL; the actual FATAL return is console evidence supplied by the user. Do not pretend RPCS3 returns `801100ff` from that syscall.

0.7 reserves the device locally, then performs the diagnostic lookup through `buzz_cell_location()`, which returns 0 and a stable seven-byte synthetic location. Probe and attach follow only on successful local lookup and probe. No native export is called to validate a synthetic ID, and FATAL has not been reclassified as success.

## Evidence boundaries

[RPCS3 cellUsbd.cpp:38-182](https://github.com/RPCS3/rpcs3/blob/39fe6c2599f3f03b68940df1cad22305e78106b9/rpcs3/Emu/Cell/Modules/cellUsbd.cpp#L38) provides the export names, but most HLE bodies are zero-argument UNIMPLEMENTED stubs returning CELL_OK. They **do not define public argument layouts or callback ordering**. The concrete public prototypes and callback types come from [PSL1GHT usb.h:491-543](https://github.com/ps3dev/PSL1GHT/blob/f649a08fd536a9e27c08c7db2d93a2d7ee4c3bbe/ppu/include/usb/usb.h#L491), checked against the game's call sites. The table below distinguishes that public contract from RPCS3's useful LV2 implementation evidence. PSDevWiki's FNID and error tables independently confirm names/codes, not these callback sequences. The CellUsbd overview page was unavailable via the web tool.

All `cellUsbd` prefixes below are literal export prefixes. `d` is a signed device ID, `p` a signed pipe ID, and `cb(result,count,arg)` returns void. For unrecognized physical IDs/pipes the saved real function is called unchanged. For the two virtual IDs, even absent-device failures stay local. There is no synthetic LV2 transfer ID or event injection.

## Exact wired game order and descriptor profile

1. Adopt existing LDD at 0x760174 after ready byte 0x78ab14 becomes 1; wait 200 ms. Reserve virtual d. Local diagnostic GetDeviceLocation(d,buf) returns 0. This diagnostic lookup is ours, not part of the game sequence.
2. Game probe 0xbcd10 -> 0xbc628: ScanStaticDescriptor(d,NULL,1), accept 054c:0002, return 0. Rejection -1 prevents attach; capacity is two dongles.
3. Game attach 0xbd300 -> 0xbd168 / allocator 0xbca88: GetDeviceLocation(d,seven bytes), match stable object; ScanStaticDescriptor(d,NULL,2), then type 4 after config, type 5 after interface until exhausted; re-read type 1. No OUT endpoint exists in this profile.
4. OpenPipe(d,NULL) and OpenPipe(d,IN descriptor), SetPrivateData(d,game object), submit product GET_DESCRIPTOR: `(80,06,0301,0409,128)`. Public submit returns 0; attach returns 0 and the game increments manager+0xa8 (0x78ab28).
5. Product completion 0x54e470 gets 64 UTF-16LE descriptor bytes and submits SET_CONFIGURATION `(00,09,0001,0000,0)`.
6. Configuration completion 0x54e440 gets `(0,0,arg)` and submits SET_INTERFACE `(01,0b,0000,0000,0)`.
7. Interface completion 0x54e4a0 submits lights `(21,09,0200,0000,7)` with `[00,L1,L2,L3,L4,00,00]`, marks setup +0x10c ready and submits InterruptTransfer(IN,buffer,8,0x54e410,arg). OUT callback 0x54e3f0 is a no-op.
8. IN completion 0x54e410 receives `(0,5,arg)`, queues five report bytes and rearms IN. Game update 0xbd638 publishes its own presence slots 00,01 at 0x78aae9 / 0x78ab0d. The plugin only reads/logs count/presence; it never writes them. HTTP readiness requires successful attachment/configuration/IN submission for **all configured dongles**.
9. Detach 0xbccc8 calls GetPrivateData(d), marks unavailable and decrements count; shutdown closes EP0/IN via 0xbb550; 0xbcdc8 unregisters LDDs and optionally calls End if initialization was owned.

Descriptors exactly retain [RPCS3 Buzz.cpp:40-97](https://github.com/RPCS3/rpcs3/blob/39fe6c2599f3f03b68940df1cad22305e78106b9/rpcs3/Emu/Io/Buzz.cpp#L40): USB 2.0, 054c:0002, bcdDevice 05a1, EP0 max 8, manufacturer index 2/product index 1, configuration total 34/value 1, interface 0/alt 0 HID, 78-byte report descriptor, interrupt-IN 81/max packet 8/interval 10. Static descriptor bytes remain USB little-endian; setup struct u16 fields are PPU native-endian, consistent with RPCS3 `UsbDeviceRequest` be_t fields in sys_usbd.h:52-59. The saved physical [buzz_descriptor_0.txt](../../research/buzz_descriptor_0.txt) agrees on topology/packet sizes but reports a different bcdDevice/manufacturer index; the selected profile follows RPCS3 consistently.

Control completion timing remains 100 us, IN 6000 us, pumped with the existing minimum 2 ms service sleep. [Buzz.cpp:121-129](https://github.com/RPCS3/rpcs3/blob/39fe6c2599f3f03b68940df1cad22305e78106b9/rpcs3/Emu/Io/Buzz.cpp#L121) and IN code above supply those simulation deadlines; they are not measured hardware guarantees. [usb_device.cpp:370-400](https://github.com/RPCS3/rpcs3/blob/39fe6c2599f3f03b68940df1cad22305e78106b9/rpcs3/Emu/Io/usb_device.cpp#L370) defines configuration/interface/string control behavior. Each request completes on a later tick; rearming never causes synchronous recursive completion.

## Validation and remaining limits

`test_game_sequence.c` replays the exact 0.6.1 fatal-return real-export mock, adoption without registration, both local lookups, public callbacks and pad masks 32768/4096/release. It also checks all 40 button bits, real pass-through and detach cancellation. `test_worker_liveness.c/.py` executes actual native wrappers and service loops with mock game callbacks and HTTP on **127.0.0.1 only**; it requires two ready dongles and `/health.json` true. Its real-location mock aborts if invoked. Host read_memory deliberately returns no game memory, so host `game state ...` lines cannot establish the retail presence fields. Hardware count=2/presence=00,01, PPU callback ABI and gameplay remain unverified.
